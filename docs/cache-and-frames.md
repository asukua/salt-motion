# 0.1.8：按专辑缓存与独立图像内存

## 问题与约束

2160×2160 HEVC 在旧 CPU 软件渲染链路约 17 FPS；在线和完整本地文件对照接近，故缓存用于加载与离线能力，不作为帧率问题已经解决的证据。用户要求保留最高画质，并明确把 GPU 路线另做实验包。正常版不引入共享 GPU 设备或 Surface，也不把已有故障路径换名后重新启用。

## 缓存

MotionVideoCache 将 AM 专辑 ID 作为视频目录键，将本地专辑身份、地区顺序及显式绑定作为查找映射键。不同歌曲及两个封面节点通过同一个同步缓存实例复用素材。缓存命中早于目录查询；一个全新 MotionRuntime 即使 HTTP 客户端已关闭仍能命中。首次按 HlsVariants 的最高分辨率、同档最高平均码率下载，不转码，不自动在命中时联网复核新素材。

只接受已结束的普通媒体 HLS 清单，排除 master、加密及未知 URI 类型。初始化块与视频分段引用统一解析为允许的 Apple HTTPS CDN 地址，去重后下载完整文件，保留 EXT-X-MAP / BYTERANGE 以维持原素材。没有把 URL 当作缓存，也没有将 MP4 附到歌曲封面标签。

下载使用原 OkHttp 客户端、逐跳 URL 校验和关闭取消，另有二进制流上限与实际长度检查。每张专辑最多 256 MiB、64 个去重资源；总缓存约 2 GiB。下载期间只写私有临时目录，完成后记录每个资源及本地清单的尺寸、SHA-256，再原子移动目录并发布映射。命中时复核全部资源；部分、损坏或条件变化的缓存不会命中。清理只删除受控的扁平临时目录，发布目录不自动淘汰，避免主动删除解码器仍使用的文件；磁盘上限/缓存异常时保留在线选流。

## 取帧内存

旧路径将每帧 bgr0 缓冲复制到 Java ByteArray，再经 Skia raster 创建图像；2160 每帧约 18.7 MB。新 readImage 路径为每帧分配独立 SkData，64 字节对齐后让软件渲染器直接写入，并以 SkData 子集创建 raster Image。Skia 保有像素引用，关闭临时 Data 及解码器不会释放仍在用的图像。行 stride 保持对齐，图像仍为所选宽高。OPAQUE 忽略 bgr0 第四字节，因此无需额外 alpha 填充。

旧 read() 保留给像素回归探针，每次恢复自己的目标指针；两种读取与关闭仍互斥。关闭后读帧先返回，不访问已释放参数。节点在帧率等待被取消或过期时关闭尚未交付的 Image，交付后由 OwnedMotionFrame 接管；绘制、替换和释放共享锁。最多两个解码器及后台退休顺序保持不变。

未采用关闭 zimg、取消目标时刻等待或将解码线程增加到八的参数改动：本机隔离样本分别约 7.30、12.91、15.40 FPS，没有优于原路径。减少额外整帧复制作为局部优化保留，不据此承诺 30。

## 实测与验证

同一 2160 本地《24K Magic》素材，512MB Java 堆、播放器裁剪运行时，7 秒预热、8 秒采样、486×486 CPU raster 绘制：旧包 138 帧 / 17.24 FPS，新独立图像路径 151 帧 / 18.86 FPS。短时单样本，不表示窗口稳定提高固定比例。原始结果位于 build/image-rate-probe/previous.log 和 owned-image.log。

CacheImageProbe 使用真实生产 prepare：下载 48,030,262 字节视频，第二个新实例关闭 HTTP 后仍复用离线素材；15 个图像均为 2160 且像素有变化。保留首帧在后续读取和解码器销毁后可编码；PNG 已查看，画面及颜色正常。单元测试覆盖清单引用去重/范围、映射隔离、部分失败清理、完整性破坏、配额/路径及二进制 HTTP 传输边界。完整运行时结果见 build/stable-final.log。

正常版、GPU 实验版与旧包以版本目录、独立文件名保留；保持 dev.saltmotion 身份，导入时切换版本，配置及已完成缓存可复用。
